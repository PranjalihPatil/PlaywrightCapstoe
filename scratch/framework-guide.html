The Big Picture

Before diving into code, let's understand what this project is and how the folders are organized.

💡
Think of it this way

Imagine you have a robot that can open a web browser, click buttons, type text, and check if things look correct — all by itself, without a human touching the mouse. That robot is Playwright. This project is the instruction manual you wrote for that robot, telling it exactly what to do on the website automationexercise.com (a fake online shop for practicing).

📌
The pattern

This framework follows the Page Object Model (POM). Think of it like a GPS app: the pages/ folder contains maps of each website page (where the buttons and fields are), and the tests/ folder contains the driving directions (what to do on those pages). Keeping maps separate from directions means if the website changes, you only update the map — not every single test.

package.json

/ package.json
This is the project's identity card. It tells Node.js the project name, what tools (packages) it needs, and what shortcut commands you can run. 
 1{
 2  "name": "playwright_agilent",
 3  "version": "1.0.0",
 4  "description": "",
 5  "main": "index.js",

Line 2 — "name": The project's name, like a name tag. It says "Hi, I'm playwright_agilent."

Line 9 — "test:first": Run only tests tagged with @first. The --grep flag filters by tag name.

Line 10 — "test:local": Run tests against a local dev server on your own computer instead of the live website.

17  "type": "commonjs",

Lines 14–16 — Standard metadata: keywords for search, author name, license type. Not critical for running tests.

Line 17 — "type": "commonjs": Tells Node to use the require() style of imports (the older, widely-supported way) instead of the newer import/export style at runtime.

tsconfig.json

/ tsconfig.json
This tells TypeScript (the programming language) how to behave. TypeScript is like JavaScript with a spell-checker — it catches mistakes before you run the code. 
 1{
 2  "compilerOptions": {
 3    "target": "ES2020",
 4    "module": "commonjs",
 5    "strict": true,
 6    "esModuleInterop": true,
 7    "resolveJsonModule": true,
 8    "types": ["node"]
 9  },
10  "include": [
11    "tests/**/*.ts",
12    "pages/**/*.ts",
13    "fixtures/**/*.ts",
14    "utils/**/*.ts",
15    "config/**/*.ts"
16  ]
17}

Line 3 — "target": "ES2020": Convert TypeScript into JavaScript that matches the 2020 standard. Modern enough to use features like async/await.

Line 4 — "module": "commonjs": Use require()-style imports when the code runs.

Line 5 — "strict": true: Turn on ALL spell-checking rules. This catches bugs like forgetting to handle null values.

Line 6 — "esModuleInterop": true: Makes it easier to import libraries that were written in different styles. Without this, some import statements would fail.

Line 7 — "resolveJsonModule": true: Lets you import JSON files directly into your TypeScript code (like the test data files).

Line 8 — "types": ["node"]: Include Node.js type definitions so TypeScript knows about things like process.env.

Lines 10–16 — "include": Tells TypeScript which folders to check. The **/*.ts pattern means "all .ts files in all subfolders." It scans tests, pages, fixtures, utils, and config.

Env

env.config.ts

config / env.config.ts
A tiny file that stores environment settings — the website address, how long to wait, and how many times to retry a failed test. 
1export const envConfig = {
2  baseUrl: 'https://automationexercise.com',
3  timeout: 30000,
4  retries: 0,
5};

Line 1 — export const envConfig: Create a settings object and export it so other files can import and use it.

Line 2 — baseUrl: The website we're testing. Every time a test goes to /login, Playwright adds this in front, making it https://automationexercise.com/login.

Line 3 — timeout: 30000: Each test gets 30,000 milliseconds (30 seconds) to finish. If it takes longer, Playwright marks it as failed.

Line 4 — retries: 0: Don't retry failed tests when running locally. (In CI, the main config overrides this to 2.)

💡
Why a separate config file?

Imagine changing the website URL. Instead of searching through 20 files, you change it in one place here, and every file that imports envConfig automatically gets the new value.

PW

playwright.config.ts

/ playwright.config.ts
The master control panel for Playwright. It tells the robot which browsers to use, where the tests are, what to do when a test fails, and more. 
 1import { defineConfig, devices } from '@playwright/test';
 2import { envConfig } from './config/env.config';

Line 1 — Import two things from Playwright: defineConfig (a function that creates a proper config) and devices (a list of pre-made browser profiles like "Desktop Chrome").

Line 2 — Import your environment settings from the config file we just learned about.

 4export default defineConfig({
 5  testDir: './tests',
 6  fullyParallel: true,
 7  forbidOnly: !!process.env.CI,
 8  retries: process.env.CI ? 2 : envConfig.retries,
 9  workers: process.env.CI ? 1 : undefined,
10  reporter: [['html', { outputFolder: 'reports' }]],
11  timeout: envConfig.timeout,

Line 5 — testDir: './tests': "Look in the tests folder for test files." Playwright will find all .spec.ts files there.

Line 6 — fullyParallel: true: Run tests at the same time, not one after another. This makes the whole suite finish faster.

Line 7 — forbidOnly: !!process.env.CI: If running in CI (a build server like GitHub Actions), block any test marked with .only. Why? Because .only means "run just this one test" — a developer might forget to remove it, and CI would accidentally skip all other tests.

Line 8 — retries: In CI, retry a failed test 2 times (sometimes tests fail due to network flakiness). Locally, use whatever envConfig says (which is 0 — no retries).

Line 9 — workers: In CI, use 1 worker (run tests one at a time for stability). Locally, undefined lets Playwright decide based on your CPU cores.

Line 10 — reporter: Generate an HTML report in the reports folder. After tests run, you can open this report in a browser to see green/red results.

Line 11 — timeout: Use the 30-second timeout from envConfig.

13  use: {
14    baseURL: envConfig.baseUrl,
15    trace: 'on-first-retry',
16    screenshot: 'only-on-failure',
17    video: 'retain-on-failure',
18  },

Line 14 — baseURL: The root address of the website. Now every page.goto('/login') automatically becomes https://automationexercise.com/login.

Line 15 — trace: 'on-first-retry': When a test fails and retries for the first time, capture a trace — a recording of every click, navigation, and network request. You can replay this trace to debug what went wrong.

Line 16 — screenshot: 'only-on-failure': Take a screenshot only when a test fails. This saves disk space while still giving you a picture of the broken state.

Line 17 — video: 'retain-on-failure': Record video of every test, but only keep the videos from failed tests. Passed-test videos are thrown away.

20  projects: [
21    {
22      name: 'chromium',
23      use: { ...devices['Desktop Chrome'] },
24    },
25    {
26      name: 'firefox',
27      use: { ...devices['Desktop Firefox'] },
28    },
29    {
30      name: 'webkit',
31      use: { ...devices['Desktop Safari'] },
32    },
33  ],

Lines 20–33 — projects: Run every test in three different browsers:

1. Chromium (the engine behind Google Chrome)

2. Firefox (Mozilla's browser)

3. WebKit (the engine behind Apple Safari)

The ...devices['Desktop Chrome'] syntax "spreads" Playwright's built-in settings for a desktop Chrome — things like screen size, user-agent string, etc.

💡
Why three browsers?

Different browsers can display the same website slightly differently. Testing in all three catches bugs that only appear in one browser. It's like proofreading your essay in three different fonts to catch hidden formatting problems.

helpers.ts

utils / helpers.ts
A small utility file with reusable helper functions — like a toolbox with tools you use in many tests. 
1export function generateRandomEmail(): string {
2  const timestamp = Date.now();
3  return `testuser_${timestamp}@test.com`;
4}

Line 1 — Creates a function called generateRandomEmail and exports it. The : string part is TypeScript saying "this function gives back text."

Line 2 — Date.now() gets the current time as a big number (milliseconds since Jan 1, 1970). Example: 1700000000000.

Line 3 — Creates an email like testuser_1700000000000@test.com. Because the timestamp is always different, the email is always unique — important because the website won't let you register the same email twice.

Page Objects

Each file below is a "map" of one page on the website. It lists all the important buttons, fields, and links, and provides functions to interact with them.

BasePage.ts

pages / BasePage.ts
The parent class that every other page inherits from. It contains shared abilities that all pages need. 
 1import { Page } from '@playwright/test';
 2
 3export class BasePage {
 4  constructor(protected page: Page) {}
 5
 6  async navigateTo(path: string) {
 7    await this.page.goto(path);
 8  }
 9
10  async getPageTitle(): Promise<string> {
11    return this.page.title();
12  }
13}

Line 1 — Import Page from Playwright. Page represents a single browser tab.

Line 3 — Create a class called BasePage. A class is like a blueprint for building objects.

Line 4 — The constructor runs when you create a new BasePage. It takes a page (browser tab) and saves it. The protected keyword means child classes (like HomePage) can also use this.page.

Lines 6–8 — navigateTo(path): Go to a URL. async and await mean "this takes time (loading a page), so wait for it to finish." When you call navigateTo('/login'), Playwright opens https://automationexercise.com/login.

Lines 10–12 — getPageTitle(): Read the page's title (the text that shows in the browser tab). Returns a Promise<string> — a promise that eventually gives you text.

💡
Inheritance analogy

Think of BasePage as a basic phone. It can make calls and send texts. HomePage, LoginPage, etc. are like smartphones — they can do everything the basic phone does, PLUS extra things like taking photos and running apps.

How It All Connects

🏗
The whole picture

When you type npx playwright test, here's what happens:

1. Playwright reads playwright.config.ts to know: which browsers, which folder, what timeout, etc.

2. It finds all .spec.ts files in the tests/ folder.

3. For each test, the fixture (base.fixture.ts) creates a fresh browser page, blocks ads, and builds page objects (HomePage, LoginPage, etc.).

4. The test runs its steps: navigate, fill forms, click buttons, check results — using the page objects as helpers.

5. Playwright repeats every test in Chromium, Firefox, and WebKit.

6. At the end, an HTML report is generated in reports/ showing which tests passed or failed.
