Playwright Test Automation Framework

A step-by-step walkthrough of our Page Object Model framework — what each file does, why it exists, and how the pieces connect.

Playwright TypeScript Page Object Model 3 Browsers
The Big Picture

What is this framework?

This is an end-to-end test automation framework built on Playwright using TypeScript. It tests the site automationexercise.com across three browsers — Chromium, Firefox, and WebKit — running in parallel.

The architecture follows the Page Object Model (POM) pattern: every web page has a corresponding class that owns all the locators and actions for that page. Tests never touch raw selectors — they call methods like loginPage.login(email, password) instead.

💡
Why POM? If a UI element changes (a button moves, a selector changes), you fix it in one page object file — not across dozens of tests. It makes tests readable, maintainable, and resistant to UI churn.

Step-by-Step Walkthrough

Every file explained, in the order you'd read them

1
Environment Configuration
config/env.config.ts
Why it exists: Centralizes all environment-specific settings in one place. If we switch to a staging URL or want to change the global timeout, we change it here — not in every test file.
export const envConfig = { baseUrl: 'https://automationexercise.com', timeout: 30000, // 30 seconds per test retries: 0, };
  • baseUrl — the app under test; all navigateTo('/path') calls resolve against this
  • timeout — how long Playwright waits before failing a test
  • retries — 0 locally (fail fast), can be changed for CI
2
Playwright Configuration
playwright.config.ts
Why it exists: This is Playwright's entry point — it tells Playwright where tests live, which browsers to run, how to report results, and what to capture on failure.
export default defineConfig({ testDir: './tests', fullyParallel: true, workers: process.env.CI ? 1 : 3, reporter: [['html', { outputFolder: 'reports' }]], use: { baseURL: envConfig.baseUrl, trace: 'on-first-retry', screenshot: 'only-on-failure', video: 'retain-on-failure', }, projects: [ { name: 'chromium', ... }, { name: 'firefox', ... }, { name: 'webkit', ... }, ], });
  • fullyParallel + 3 workers — tests run simultaneously across browsers for speed
  • HTML reporter — generates a browsable report in reports/
  • trace on first retry — captures a full trace (network, DOM, screenshots) when retrying
  • screenshot + video on failure — automatic evidence capture for debugging
3
Custom Fixtures (Dependency Injection)
fixtures/base.fixture.ts
Why it exists: This is the heart of the framework's ergonomics. Instead of creating page objects manually in every test, fixtures inject them automatically. Tests just declare what they need.
export const test = base.extend<PageFixtures>({ page: async ({ page }, use) => { // Block ad network requests await page.route( /google(ads|syndication)|doubleclick/, (route) => route.abort() ); await page.waitForTimeout(5000); await use(page); }, homePage: async ({ page }, use) => { await use(new HomePage(page)); }, loginPage: async ({ page }, use) => { await use(new LoginPage(page)); }, productsPage:async ({ page }, use) => { await use(new ProductsPage(page)); }, cartPage: async ({ page }, use) => { await use(new CartPage(page)); }, // ... checkoutPage, contactUsPage });
💡
What is a fixture? Think of it as a "setup recipe" that Playwright runs before your test. When a test parameter says { loginPage }, Playwright automatically creates a LoginPage instance and hands it to the test. No manual setup code needed. The fixture also blocks ad requests so third-party scripts don't interfere with our tests.
  • Ad blocking — routes matching google ads / doubleclick are aborted, preventing flaky failures from ad scripts
  • 5-second wait — gives the page time to stabilize after navigation
  • All tests import from here — import { test, expect } from '../fixtures/base.fixture' instead of @playwright/test
4
Base Page Object
pages/BasePage.ts
Why it exists: Every page object extends this class. It holds shared methods that all pages need — right now that's navigateTo() and getPageTitle(). As the framework grows, shared helpers go here.
export class BasePage { constructor(protected page: Page) {} async navigateTo(path: string) { await this.page.goto(path); } }
  • Receives the Playwright page object via constructor
  • navigateTo('/login') resolves against the baseURL from config
  • Child classes inherit this, so they can call this.navigateTo() directly
5
Home Page Object
pages/HomePage.ts
Why it exists: Encapsulates all interactions with the home page — navigation links, checking login state, accessing cart. Tests call homePage.clickLogout() instead of knowing the selector.
  • Locators: signup/login link, logged-in user text, logout link, cart link
  • Methods: navigate(), getLoggedInUsername(), clickSignupLogin(), clickLogout(), clickCart()
6
Login Page Object
pages/LoginPage.ts
Why it exists: Handles both login and user registration. The fillRegistrationForm() method fills all 15+ fields using data from the user object — keeping test code clean.
  • login(email, password) — fills email/password fields, clicks login button
  • signup(name, email) — fills signup fields, clicks signup button
  • fillRegistrationForm(userData) — fills full registration form (gender, DOB, address, phone) and submits
  • Uses [data-qa="..."] selectors — stable test-specific attributes the site provides
7
Products Page Object
pages/ProductsPage.ts
Why it exists: Handles product browsing — searching, counting results, and the add-to-cart flow including the confirmation modal.
  • searchProduct(term) — types into search and clicks the search button
  • getProductCount() — returns the number of visible products
  • addProductToCart(index) — scrolls to a product and clicks its "Add to Cart" button
  • clickContinueShopping() / clickViewCartInModal() — handles the modal that appears after adding
8
Cart Page Object
pages/CartPage.ts
Why it exists: Encapsulates cart verification — counting items, reading product names, removing products, and proceeding to checkout.
  • getCartItemCount() — returns number of rows in the cart table
  • getProductName(index) — reads the product name from a specific row
  • removeProduct(index) — clicks the delete button on a row
  • clickProceedToCheckout() — moves to the checkout step
9
Checkout Page Object
pages/CheckoutPage.ts
Why it exists: Handles the multi-step checkout — verifying the delivery address, adding order comments, placing the order, and filling payment card details.
  • verifyAddressVisible() — confirms the delivery address section is showing
  • addComment(comment) — fills the order comment textarea
  • clickPlaceOrder() — clicks the Place Order button
  • fillPaymentDetails(payment) — fills card name, number, CVC, expiry and submits
10
Contact Us Page Object
pages/ContactUsPage.ts
Why it exists: Wraps the contact form — filling all fields and submitting. The success message locator is stored here so tests can assert against it.
  • fillForm(data) — fills name, email, subject, message from a data object
  • submitForm() — clicks the submit button
  • successMessage — locator for the success alert (used in test assertions)
11
Test Data
testdata/users.json & contactUs.json
Why they exist: Test data lives in JSON files, separate from test logic. This makes it easy to add new test data scenarios without touching test code — and keeps tests clean and readable.
// users.json — valid user + invalid login combos { "validUser": { "name": "TestUser", "password": "Test@1234", "firstName": "Test", "lastName": "User", "country": "United States", ... }, "invalidLogins": [ ... ] }
12
Utility Helpers
utils/helpers.ts
Why it exists: Shared helper functions that tests need but don't belong to any page. Right now it has one function — generating unique emails so each test run creates a fresh account.
export function generateRandomEmail(): string { return `testuser_${Date.now()}@test.com`; }
Test Files

What each test covers

Every .spec.ts file is a test suite. Here's what each one validates and the testing technique it demonstrates.

Test File What It Does
auth.spec.ts Register → Login → Logout. Runs in serial order because each test depends on the previous one (must register before logging in). Uses generateRandomEmail() so each run gets a fresh account.
cart.spec.ts Add 2 products → verify cart count. Remove a product → verify cart is empty. Demonstrates the add-to-cart modal flow and cart state verification.
checkout.spec.ts Full end-to-end checkout. Registers a user, adds a product, proceeds through checkout, fills payment details, verifies "order confirmed" message. The longest user journey in the suite.
contactUs.spec.ts Contact form submission. Fills the form from JSON data, handles the browser confirmation dialog with page.on('dialog'), verifies the success message.
productSearch.spec.ts Three tests in one file: (1) Search for "top" and verify results appear. (2) Network interception — captures the search request and asserts the URL contains the search term. (3) API mocking — intercepts /api/productsList and returns a fake response.
accessibility.spec.ts Accessibility scan using @axe-core/playwright. Runs the axe engine on the home page, filters for critical violations, and allows at most 3. Catches issues like missing alt text, broken ARIA roles, low contrast.
visualRegression.spec.ts Screenshot comparison. Takes a screenshot of the home page (hides dynamic elements like carousels), compares it against a stored baseline with 5% pixel diff tolerance. Catches unintended visual changes.
How It All Connects

The execution flow

Here's what happens when you run npm test:

  • Playwright reads playwright.config.ts → learns test directory, browsers, timeouts
  • Config pulls settings from config/env.config.ts → baseURL, timeout, retries
  • Each test file imports { test, expect } from fixtures/base.fixture.ts
  • The fixture creates a page with ad-blocking, then instantiates page objects on demand
  • Page objects extend BasePage.ts and use its navigateTo()
  • Tests call page object methods → page objects interact with the browser
  • Test data comes from testdata/*.json files
  • Results → HTML report in reports/, with screenshots/video on failure
Running Tests

Available NPM scripts

Command What It Does
npm test Run all tests across all 3 browsers in parallel
npm run test:chromium Run only on Chromium (fastest for local development)
npm run test:UI Open Playwright's interactive UI mode — watch tests run, step through, debug
npm run test:report Run all tests then open the HTML report in the browser
Key Patterns

Techniques used in this framework

Pattern Where & Why
Page Object Model All pages/*.ts files. One class per page — locators and actions encapsulated. Tests stay clean and selectors are maintained in one place.
Custom Fixtures fixtures/base.fixture.ts. Page objects injected into tests automatically. No boilerplate new LoginPage(page) in every test.
Data-Driven Testing testdata/*.json. Test data separated from logic. Easy to add scenarios without changing test code.
Ad Blocking Fixture's route interception. Blocks third-party ad scripts that cause flaky failures and slow down tests.
Cross-Browser playwright.config.ts projects. Every test runs on Chromium, Firefox, and WebKit automatically.
Network Interception productSearch.spec.ts. Captures real requests for assertion, and mocks API responses for isolated testing.
Accessibility Testing accessibility.spec.ts. @axe-core/playwright integration scans for WCAG violations.
Visual Regression visualRegression.spec.ts. toHaveScreenshot() compares against baselines with a pixel diff threshold.
